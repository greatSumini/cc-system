# cc-usage-audit — 분석 방법론

`scripts/extract-prompts.mjs` 가 뽑아낸 사용자의 *실제 프롬프트* 를 원자료로
삼아, ① 사용 패턴 정량화 → ② 개발 철학 추출 → ③ 메타 시스템 audit →
④ 개선점 발굴 까지 가는 절차. **신뢰도가 생명이다 — 철학을 지어내지 말고
사용자의 발화에서 추출하고, 모든 주장은 인용·수치로 뒷받침한다.**

## 0. 원칙

- **사용자의 말이 source of truth.** 모든 원칙·개선점은 특정 프롬프트(날짜·
  워크트리)로 추적 가능해야 한다. 인용 없는 주장은 쓰지 않는다.
- **정량 우선.** "자주", "많이" 대신 "70건 중 12건(17%)" 처럼 센다.
- **사용자는 최종 검증자.** 추출한 철학은 가설이다. 어긋날 수 있음을 명시하고
  사용자에게 검수를 요청한다.

## 1. 사용 패턴 정량화

`extract-prompts.mjs` 가 이미 출력하는 것: 프롬프트 수, 길이 분포, 시간대,
워크트리(=작업 단위)별 분포. 여기에 **주제 분류**를 더한다.

추출된 프롬프트를 읽고 반복 주제로 분류해 빈도를 센다. 분류는 프로젝트마다
다르지만, 대개 아래 축이 신호가 된다:

| 축 | 무엇을 세나 | 무엇을 시사하나 |
| --- | --- | --- |
| 반복 잡일 지시 | 동일 의도가 N회 (예: "commit push pr merge") | skill/자동화 후보 (ROI = N×미래빈도) |
| 메타 시스템 의문 | 하니스/게이트/설정을 "왜 이래야 하나" 질문 | 과설계·강결합 신호 |
| 비판적 논쟁 요구 | "한판 붙자", "비판적으로", "어떻게 생각해" | 사용자가 중시하는 의사결정 지점 |
| 재확인/불신 | "다시 체크", "진짜 맞아?" | 검증 자동화 부재 / 신뢰 부족 지점 |
| 언어/스타일 교정 | "한글로", "괜히 영어 쓰지마" | 기본 설정(CLAUDE.md)으로 제거 가능한 마찰 |
| 재전송/보강 | 직전 프롬프트의 near-duplicate | 프롬프트↔이해 마찰 |
| 시간대 집중 | 특정 시간대(예: 심야)에 쏠림 | 무인/배치 워크플로 필요성 |

간단한 빈도 카운트는 다음으로 충분하다(예시):

```bash
node -e '
const a=require("/tmp/p.json").filter(o=>!o.text.startsWith("<task-notification>"));
const re=/commit|push|pr |squash|merge/i;
console.log(a.filter(o=>re.test(o.text)).length, "/", a.length);'
```

## 2. 개발 철학 추출

분류된 신호에서 **반복적으로 드러나는 가치/본능**을 원칙으로 승격한다.
각 원칙은 반드시 **주장 / 근거(직접 인용 + 날짜) / 함의** 세 줄로 적는다 —
이래야 추적·반박이 가능하다.

```
### P{n}. <한 문장 주장>
- 근거: _"<사용자 발화 그대로>"_ (YYYY-MM-DD, <worktree>).
- 함의: <이 원칙이 메타 시스템 점검에서 무엇을 요구하는가>.
```

원칙은 5~9개로 압축한다(많으면 서로 겹친다). 서로 긴장하는 원칙쌍(예:
"최소주의" vs "정직성")이 있으면 그 긴장을 *해소하는 규칙*까지 명시한다 —
거기서 가장 쓸모 있는 지침이 나온다.

흔히 발견되는 원칙 (프로젝트마다 검증할 것, 복붙 금지):

- 메타 시스템은 제품의 종(從) — 메타가 제품을 압도하면 결함.
- 중복 검증은 빚 — "이게 깨지면 어떤 테스트가 빨개지나?" 답 있으면 빼라.
- 양식이 아니라 의도를 검증 — 함수명/경로 grep = 강결합.
- 데이터 없이 결정 안 함 — 추측 금지, 재현·측정.
- 검증자를 검증 — "됐다"를 액면으로 믿지 않음.
- 순응이 아니라 논쟁 — 점검자가 반박할 수 있어야.

## 3. 메타 시스템 audit (철학을 렌즈로)

추출한 철학을 **의심 질문 + 검증 방법 + 판정**으로 바꿔, 대상 산출물에
적용한다. 대상은 프로젝트의 "메타 시스템" — 보통:

- 하니스/게이트 스크립트 (`*.gates.sh`, `*.next-task.sh`, `scripts/`)
- 자동화 설정 (`.claude/settings.json` hooks, CI 워크플로)
- 프로세스 문서 (findings/cycle/guideline 프로토콜)

각 산출물(가능하면 블록/파일 단위)에 대해:

1. **정량 측정**: `wc -l`, 파일 수, 실행 빈도/비용, 제품 코드 대비 비율.
   "하니스 LOC ÷ 제품 소스 LOC" 같은 비율은 과설계를 가장 잘 드러낸다.
2. **의심 질문 적용**: 철학에서 도출한 질문을 던진다. 핵심 휴리스틱 —
   - "이 검사가 없으면 어떤 *테스트/타입체크* 가 잡는가?" (잡으면 중복)
   - "무해한 리팩터에 spurious fail 하는가?" (하면 양식 강결합)
   - "이건 영속 진실인가, 초기 추측인가?" (추측이면 화석화 위험)
   - "이 'resolved/green' 주장을 무엇으로 검증했나?" (재현해 확인)
   - "이 변경은 검증을 *약화* 하나, *이전* 하나?" (약화면 정직성 위반)
3. **반박 테스트**: 산출물을 *없애자/뒤집자* 는 입장을 한 번 세워 그래도
   살아남는지 본다. 살아남지 못하면 개선 대상.
4. **판정**: KEEP / TRIM / MOVE-TO-TEST / DELETE(단 선언·테스트 이전 동반) /
   DEFER. **검증 약화를 통한 통과는 절대 금지.**

> 프로젝트에 이미 audit 지침 문서(예: `guidelines/meta-system-audit.md`)가
> 있으면 그것을 단일 출처로 삼고 중복 생성하지 말 것. 없으면, 추출한 철학을
> 그런 지침으로 남기자고 제안한다.

## 4. 개선점 발굴 + 우선순위

audit 결과 + 패턴 신호를 합쳐 개선점을 뽑고, **영향 × 근거강도**로 정렬한다.

- **반복 잡일** → skill/스크립트/hook 후보. ROI = (과거 빈도) × (미래 빈도).
- **과설계/강결합** → trim/이전 대상 (정직성 규칙 준수).
- **마찰(재확인·교정·재전송)** → 기본 설정·검증 자동화로 제거.
- **제품에서 먼 비싼 메타 작업** → deferral 후보.

각 개선점에 **신뢰도 라벨**을 붙인다:

- **높음**: 직접 인용 + 정량(빈도/LOC) 둘 다.
- **중간**: 분류 기반 비율 추정 (해석 여지 있음).
- **참고**: 기존 문서/finding 이 이미 진단한 것의 재확인.

## 5. 산출물

- 5개 관점(또는 프로젝트에 맞는 축)별 개선점 표 + 우선순위 종합 표.
- 추출한 철학은, 사용자가 원하면 프로젝트 지침 문서로 남긴다(중복 금지).
- **즉시 수정하지 않는다** — 발굴/문서화가 이 skill 의 범위. 수정은 사용자가
  별도로 지시하거나, ship/구현 skill 로 이어간다.
